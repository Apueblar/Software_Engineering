Part II — Open Questions
OQ1
What are the key distinctions between measures and dimension attributes? Briefly justify your answer.
Key points: Measures are numeric, quantitative values that can be aggregated (summed, averaged, etc.) — e.g. revenue, quantity sold. Dimension attributes are descriptive, qualitative labels used for filtering and grouping — e.g. product name, region, date. Measures describe what happened; dimensions describe the context in which it happened.
OQ2
How would you modify the schema to include information about an employee being associated with a particular Supplier (an employee can be associated with multiple suppliers)?
Key points: Since an employee can be associated with multiple suppliers, there is a many-to-many relationship. You cannot simply add a SupplierID to the Employee dimension. Instead, create a bridge/associative table EmployeeSupplier(EmployeeID, SupplierID). This is a dimension bridge table pattern in Kimball's methodology. If the association needs to be tracked over time, surrogate keys and SCD handling should be applied.
OQ3
How would you handle (within an ETL process) a situation in which an order is missing employee details?
Key points: Use a default/unknown dimension record — a special row in the Employee dimension (e.g. EmployeeID = -1 or 0) with placeholder values like "Unknown" or "N/A". During ETL, orders missing employee details are assigned this surrogate key instead of leaving the foreign key NULL. This preserves referential integrity and allows the fact to still be counted and aggregated correctly without data loss.

ETL & Data Integration (Lecture 4)

Foundational
Summary
ETL extracts and transforms data externally before loading; ELT loads raw data into scalable cloud targets first and transforms in-place. Data Profiling (structure, content, business rules) is the mandatory first step. Quality is defined by Kimball's 5C's (business view) and DAMA's 6 dimensions (technical view).
📊 ETL Phases & CDC
  • Extraction — pull data from source systems.
  • Transformation — cleanse, harmonise, derive, aggregate.
  • Loading — write to DW (full or incremental).
  • CDC — detects row-level changes (timestamp, triggers, log-based).
✨ Data Quality Frameworks
  • Kimball's 5C's: Clean, Consistent, Conformed, Current, Comprehensive.
  • 6 DAMA Dimensions: Accuracy, Validity, Consistency, Uniqueness, Timeliness, Completeness.
  • Data Profiling Screens: Structure, Content, Business Rule.
🎯 Exam trap: 5C's are Kimball's business language; 6D are the technical measurement dimensions. A "Conformed" business goal maps to both Uniqueness and Consistency technically.

Data Warehouses: Definitions & Architecture (Lecture 5)

Architecture
Summary
Inmon's DW is subject-oriented, integrated, time-variant, and non-volatile — a read-only historical store for decision-making, contrasting with volatile OLTP systems. The ecosystem adds an ODS for near-real-time current data and Data Marts as subject-specific DW subsets for individual departments.
🎮 Inmon's 4 Characteristics
  • Subject-Oriented — organised around business subjects.
  • Integrated — resolves inconsistencies from multiple sources.
  • Non-Volatile — data is read-only (frozen) once loaded.
  • Time-Variant — contains historical snapshots.
⚡ DW Components & Grain
  • Staging Area: ETL processing (no business users).
  • Organisation Area: multidimensional data model (direct querying).
  • Access Area: BI tools and reporting.
  • Granularity: level of detail (multiple levels kept simultaneously).
03 🧊

Multidimensional Data Model (Lecture 6)

Core
Summary
Data is modelled as Facts (measurable events) and Dimensions (descriptive context). The Star Schema denormalizes dimensions for speed; the Snowflake Schema normalizes them. OLAP cubes enable rapid slicing, dicing, and aggregation via ROLAP (relational) or MOLAP (array-based) storage.
🔄 DW Schemas
  • Star Schema: central fact table + denormalised dimension tables. Fast and simple.
  • Snowflake Schema: normalised dimensions (hierarchy levels are separated into tables). Because of this, the fact table is NOT directly connected to at least one dimension table (the outriggers).
  • Fact Constellation: multiple fact tables sharing conformed dimensions.
  • Schema Math: Analysing "monthly sales in branches" requires 3 dimensions (Time, Branch, Product). Analysing "number and value" requires 2 measures.
🧠 Storage Types
  • ROLAP (Relational): data stored in RDBMS.
  • MOLAP (Multidimensional): data stored in multidimensional database (MDBMS).
🎯 Key rule: If an attribute is commonly aggregated → it's a fact. If an attribute drives aggregations → it's a dimension.
04 📊

Dimensions, OLAP Operations & Architectures (Lecture 7)

OLAP
Summary
OLAP enables interactive navigation via Roll-up, Drill-down, Slice, Dice, and Pivot. Measures are additive (sum across all dims), semi-additive (e.g., balances — not across time), or non-additive (e.g., ratios). Hierarchies (Day→Month→Year) structure the drill paths within dimensions.
OLAP Operations & Hierarchies
Drill Down / Roll UpNavigate between coarse and detailed levels of aggregation.
Slice / DiceFilter on one (Slice) or multiple (Dice) dimensions.
Drill-AcrossQuery multiple fact tables via conformed dimensions.
HierarchiesDefined between attributes from a single dimension table (e.g., Day → Month). Handled via flattening (Star) or snowflaking (Snowflake).

Dimensional Model Details (Lecture 8)

Modelling
Summary
Fact tables come in three types: Transaction (one row per event), Periodic Snapshot (regular status measurements), and Accumulating Snapshot (updated as an entity moves through milestones). Special dimensions include Conformed, Junk, Degenerate, and Role-Playing. Measures are Distributive, Algebraic, or Holistic based on how they can be partitioned and recomputed.
📐 Fact Table Types & Cubes
  • Transaction: one row per event (append only). Grain = individual transaction.
  • Periodic Snapshot: status measurement at intervals (e.g., monthly balances). Dense snapshots.
  • Accumulating Snapshot: updated as an entity progresses through milestones. Tracks lags (days between steps).
  • Factless Fact: captures occurrences/events without numerical measures (e.g., student attendance).
  • Base Cuboid (N-D): Lowest level of summarization for all N dimensions.
  • Apex Cuboid (0-D): Highest level of summarization (total sum over all dimensions).
🔬 Special Dimensions & Keys
  • Conformed Dimension: shared across multiple fact tables, enabling drill-across queries.
  • Junk Dimension: groups miscellaneous low-cardinality flags (under 26 dims).
  • Degenerate Dimension: high-cardinality key (e.g. Order ID) stored directly inside the fact table with no separate dimension table.
  • Role-Playing Dimension: referenced multiple times for different roles (e.g., order date, ship date).
  • Surrogate Keys: Anonymous integer primary keys assigned in sequence. Protects DW from operational source changes.
  • Durable Supernatural Key: A persistent integer key for an entity that never changes, even if multiple surrogate keys exist over time due to SCD tracking.
🌲 Hierarchies & Drilling
  • Balanced Hierarchy: Fixed number of clearly defined levels (e.g., Time).
  • Unbalanced/Ragged Hierarchy: Recursive self-joins (e.g., employee to manager). Handled using a Hierarchy Bridge Table (contains parent_id, sub_id, levels_removed). Flattening is a limited alternative.
  • Drill Down: Simply adding a row header (dimension attribute) to the GROUP BY expression in a SQL query.
🔢 Types of Measures
  • Distributive: Computed by partitioning data, computing sub-aggregates, and combining them (e.g., SUM, MIN, MAX, COUNT).
  • Algebraic: Requires a consolidating function at the final stage (e.g., AVG = SUM/COUNT, Standard Deviation).
  • Holistic: No constant bound on storage size needed to describe a sub-aggregate (e.g., MODE, MEDIAN, RANK).
06 ⏳

Slowly Changing Dimensions (SCD) (Lecture 9)

SCD
Summary
SCDs manage how dimensional attributes change over time. Type 1 overwrites (destroys history), Type 2 adds a new row (full history, requires surrogate keys), Type 3 adds a column (one prior value). Types 5, 6, and 7 are combinations. Key exam fact: Type 6 = 1+2+3, Type 5 = 1+4.
SCD Types
Type 0Passive: value never changes; changes are completely ignored. Ideal for "original" attributes (e.g. credit score at account opening).
Type 1Overwrite: old value lost; only current data kept. Very easy to implement but destroys history.
Type 2New Row: full history preserved by creating a new version of the record. Requires surrogate keys. Best for year-over-year comparisons (e.g., sales by historical rating).
Type 3New Column: one prior value preserved in the same row. Sometimes called an alternate reality, allowing grouping by current or historical values without joins.
Type 4History Table / Mini-Dimension: volatile attributes split into a separate, rapidly changing table.
Type 5Type 1 + 4: Embeds a "current profile" mini-dimension key in the base dimension that is overwritten as a Type 1 attribute.
Type 61+2+3: combines overwriting, new rows, and historical columns.
Type 7Dual Type 1 & 2: Adds the natural key to the fact table for direct connection to the current profile, bypassing the surrogate key for "as-is" analysis.
🎯 Quiz trap: Type 6 = 1+2+3. Type 5 = 1+4. Type 7 achieves Type 6 results via dual keys instead of column overwrites.

Dimensional Design (Lecture 10)

Design
Summary
Kimball's 4-Step Process: choose the business process → declare the grain → identify dimensions → define measures. Design strategies range from Top-Down (Inmon) to Bottom-Up (Kimball). Conceptual tools like DFM and Dot Modelling bridge requirements to physical schemas.
📐 4 Steps of Dimensional Modelling
  • Step 1: Choose Process — a business event (not a department). The grain of the process defines the atomic level.
  • Step 2: Choose Grain — the finest level of detail (e.g., individual POS transaction line item). Declare before dimensions.
  • Step 3: Choose Dimensions — all the context (who, what, where, when). Ask "How do business people describe the data?"
  • Step 4: Define Measures — the numeric facts tied to the grain. Must be consistent and additive at the declared grain.
✨ Conceptual Modelling Techniques
  • Dot Modelling: Dot = central facts. Arrows = hierarchy paths. Separate worksheets for Data Model, Entities, Hierarchies, Fact Usage Matrix.
  • DFM (Dimensional Fact Model): Tree-structured visual schema. Handles cross-dimensional attributes (e.g., VAT depending on both Product AND Country) using circular arcs.
  • StarER: Combines Star schema performance with ER model semantics.
  • ME/R Model: E/R specialization explicitly for multidimensional structures.
⚖️ Design Strategies
  • Top-Down (Inmon): Normalized EDW first → feeds dependent data marts. High integration but slow delivery.
  • Bottom-Up (Kimball): Atomic data marts first via Enterprise Bus. Fast ROI.
  • Hybrid: Core normalized DW + parallel dimensional marts. Uses ODS and Data Vaults for flexibility.
  • Supply-Driven: Driven by available sources. Risk: collecting unused data.
  • Demand-Driven: Driven by user requirements. Risk: users may not know what's possible.
🔑 Enterprise Bus Matrix
  • A grid: Business Processes (rows) vs Conformed Dimensions (columns).
  • Used by Kimball to coordinate integration across marts without a monolithic EDW.
  • Conformed Dimension: Same attributes and keys across multiple fact tables.
  • Drill-Across: Query joining two fact tables via shared conformed dimensions.

Physical Aspects of OLAP (Lecture 13)

Physical
Summary
A full N-dimensional cube has 2N cuboids. Partial materialization (lattice) gives the best cost/performance trade-off but requires a cuboid selection mechanism. Bitmap Indexes suit low-cardinality columns; Columnar Storage (vertical partitioning) drastically cuts I/O for analytical queries.
🧱 Materialization
  • Full Materialization: All 2N cuboids pre-computed. Maximum query performance, massive storage cost.
  • No Materialization: All queries computed on-the-fly from base data. Zero storage overhead, slowest queries.
  • Partial Materialization: A selected subset of cuboids pre-computed. Requires an additional cuboid selection mechanism to route queries to the correct aggregate table. Best trade-off.
  • Lattice of Cuboids: Visual representation showing which cuboids can be derived from which. Higher-level cuboids can be computed from lower ones.
⚡ Indexes & Storage
  • Bitmap Index: One binary vector (bit string) per dimension attribute value. Very compact for low-cardinality columns. Enables fast AND/OR operations.
  • Join Index: Pre-materializes the join between fact and dimension tables as a set of RID lists. Eliminates join cost at query time.
  • Columnar Storage: Each column stored separately (vertical partitioning). Enables compression (repeated values), and only loads columns needed by a query.
  • Partitioning: Horizontal split of a table (by date range, region). Enables partition pruning to skip irrelevant data entirely.
🎯 Exam trap: Columnar storage = vertical partitioning applied systematically across all columns. It is NOT about partitioning rows.

Partial Cube Materialization saves space and ETL time but explicitly requires additional mechanisms for cuboid selection at query time to route queries to the correct aggregate table.

Logical Data Map & ETL Design (Lecture 9)

ETL Design
Summary
The Logical Data Map is the ETL blueprint — it maps every target attribute to its source, transformation logic, data types, and anomaly handling before any code is written. Skipping it forces developers to make critical business decisions in isolation, leading to integration failures.
Logical Data Map Columns
Target Table / ColumnThe destination attribute in the DW dimensional model.
Source Table / ColumnThe originating field in the source system.
Transformation LogicExact business rule applied (e.g., UPPER(last_name), COALESCE(val,0)).
Data TypeSource and target data types (mismatches are a common bug source).
Anomaly HandlingWhat to do with NULLs, out-of-range values, or missing FK references.
Test CasesSpecific examples to validate correctness of the transformation rule.
💡 Key principle: The Logical Data Map forces business decisions to be made before physical coding begins. Without it, developers make critical data interpretation decisions in isolation — a recipe for disaster.

ETL Staging, Data Quality & Architecture (Lecture 10)

Staging
Summary
The Staging Area isolates ETL workloads from source systems and enables checkpoint restarts. Load sequence: static dims → SCD Type 1 → SCD Type 2 → other dims → fact tables last (via surrogate key lookup). Data quality flows SOR → SOI → SOA.
🚦 Load Sequencing
  • Step 1: Permanent / static dimensions (Date, etc.).
  • Step 2: SCD Type 1 updates (overwrite).
  • Step 3: SCD Type 2 inserts (new rows).
  • Step 4: Remaining dimension types (junk, mini-dims).
  • Step 5: Fact tables — using surrogate key lookups from already-loaded dimensions.
  • Late-Arriving Facts: Look up the dimension row valid at the fact's event date, not current date.
  • Late-Arriving Dimensions: Insert a placeholder row, back-fill once the real data arrives.
🔒 Staging Properties
  • No surrogate keys — stores natural keys from source systems.
  • No indexes (for fast bulk inserts) — indexes added post-load.
  • Temporary: can be truncated after each successful DW load cycle.
  • Enables incremental loads by comparing current vs. previous snapshots (full diff).
  • Audit columns: ETL batch ID, load timestamp, source system ID added to every row for full lineage.

BI Ecosystem (Lecture 1 & 5)

BI
Summary
Classic stack: SQL Server → SSIS (ETL) → SSAS (cubes) → SSRS/Power BI (reporting). Modern stack: cloud MPP engines (Snowflake, BigQuery), Lakehouses (Delta Lake), streaming (Kafka), and self-service BI. Architectures evolve towards Data Mesh (domain ownership) and Data Fabric (governed integration).
🧰 Microsoft BI Stack
  • SQL Server: Relational OLTP + DW engine.
  • SSIS: SQL Server Integration Services — ETL tool (data pipelines).
  • SSAS: SQL Server Analysis Services — Multidimensional OLAP cubes and Tabular models.
  • SSRS: SQL Server Reporting Services — Paginated reports.
  • Power BI: Self-service visualization + semantic model.
☁️ Modern BI Trends
  • Cloud MPP: Snowflake, BigQuery, Azure Synapse — massively parallel analytical SQL.
  • Data Lake: Raw storage (S3, ADLS). Schema-on-read. Risk: data swamp.
  • Lakehouse: ACID + DW on top of a data lake (Delta Lake, Apache Iceberg).
  • Streaming: Kafka + Flink for real-time pipelines (sub-second latency).
  • Data Mesh: Domain teams own their data as products. Federated computational governance.
  • Data Fabric: Metadata-driven integration layer across heterogeneous stores.

ETL (Extract, Transform, Load) (Lecture 11)

ETL
Summary
ETL consumes ~70% of DW project effort. CDC enables incremental extraction. Transformation applies Column/Structure/Business Rule quality screens and data conforming. The Load phase generates surrogate keys and handles late-arriving data — never use NULLs for missing FK references, use a default key (e.g., -1).
🔧 Extraction & Loading
  • Extraction: Push vs Pull; Online vs Offline.
  • CDC: Crucial for incremental loads. Requires the ability to identify precisely which data elements have changed.
  • Loading: Generate surrogate keys in ETL, handle late-arriving facts, execute checkpointed massive loads.
  • Missing Data: Never use NULLs in fact tables for missing dimensions; assign a default surrogate key (e.g., -1 for "Unknown").
🧹 Clean & Conform
  • Quality Screens: Filters implementing tests in the data flow. Categories: Column Screens (unexpected NULLs/ranges), Structure Screens (PK/FK integrity), Business Rule Screens (customer logic).
  • Error Handling: Error Event Schema to log violations without halting execution.
  • Conforming & Units: Aligning disparate systems (e.g., transforming cm to mm to match a target standard representation).
  • Data Observability: Proactive ML-based monitoring of pipelines (volume, arrival time, lineage) vs. static Data Quality checks ("Does this column have nulls?").

Data Visualisation (Lecture 14)

Visualisation
Summary
Choose charts by comparison type: bar/column for ranking, line for time trends, scatter for correlation. Effective dashboards follow ACES (Accurate, Clear, Empowering, Succinct), use the Z-pattern, limit to 7±2 widgets, and maximize the data-to-ink ratio. Pre-attentive attributes (colour, size, shape) guide the viewer's eye instantly.
📊 Chart Selection Guide
  • Ranking (Item): Horizontal Bar (many items), Column (few items).
  • Time Dynamics: Line chart (continuous trend), Column (discrete periods).
  • Composition (Structure): Stacked Bar / Pie / Donut (use sparingly — hard to compare angles).
  • Correlation: Scatter / Dot chart.
  • Distribution: Histogram, Box Plot.
  • Geospatial: Map / Choropleth chart.
🖥️ Dashboard Design Rules
  • ACES Framework: Accurate (correct data), Clear (unambiguous), Empowering (actionable), Succinct (concise).
  • 5-Second Rule: Key message grasped within 5 seconds.
  • Z-Pattern: Most critical info in top-left. Eye scans Z-shape.
  • 7±2 Widgets: Limit cognitive load (Miller's Law).
  • No Scrolling: All critical info visible above the fold.
  • Data-to-Ink Ratio: Remove non-data ink (gridlines, borders, 3D effects).
  • Consistent Colour: Same colour = same meaning across all widgets.
🧠 Pre-attentive Attributes
  • Brain processes instantly without conscious effort: colour (hue, intensity), shape, size, position, orientation, motion.
  • Use sparingly — encoding too many simultaneously defeats their purpose.
  • Pop-out effect: A single differently-coloured item spotted in <200ms.
  • Strategically using pre-attentive attributes directs attention to the most important insight on a dashboard.
📋 KPI & Report Types
  • KPI (Key Performance Indicator): Quantifiable metric tied to a business goal. Must show: target, actual, and trend.
  • Operational Report: Detailed row-level transaction data for daily operations.
  • Analytical Report: Summarized, cross-dimensional, trend-based for decision-making.
  • Self-service BI: Power BI / Tableau allow business users to build their own reports without IT involvement.
⚠ Exam trap: Dashboard effectiveness depends on accurate underlying data first — a beautiful dashboard with bad data is worse than no dashboard. Also: Pie charts are almost always the wrong choice when comparing values (use bar charts instead).

📝 Final Exam — Parts 3 & 4 (MCQ)
9. A hierarchy in a dimensional model can be defined:
a) Between attributes of different dimensions
b) Between different measures
c) Between attributes from a single dimension with a self-join relation
d) Between dimension's attributes with a strict n:n relationship
✅ Best Answer: c) — Hierarchies often map attributes within a single dimension table. (Note: Answers are inferred based on DW theory)
10. In a snowflake schema?
a) A fact table is not directly connected to at least one dimension table
b) Multiple fact tables are directly connected to each other forming
c) A fact table is directly connected to each dimension table
d) Multiple fact tables are connected through dimension tables to each other
✅ Best Answer: a) — Because dimensions are normalized, some dimensions (outriggers) only connect to base dimensions, not directly to the fact table.
11. Snowflake schema is typically used when:
a) Higher data redundancy in dimensional table is not an issue/problem
b) Fact table consists of multiple parallel hierarchies – to separate them
c) Dimension table contains a certain group of attributes which values are often missing – to separate them
d) Dimension table has multiple levels (with multiple attributes each) in a hierarchy – to separate them
✅ Best Answer: d) — Normalizing hierarchical levels (e.g., City -> State -> Country) into separate tables creates the snowflake shape.
12. In a minimal schema to cover a simple request of analysing daily and hourly number of passing by sedan and SUV vehicles in different intersections we need (do not count surrogate keys):
a) Fact table with 1 measure
b) Snowflake schema with 5 dimensions
c) Fact table with 2 measures
d) Star schema with 3 dimension tables
✅ Best Answer: d) — 3 dimensions (Time/Date, Vehicle Type, Intersection) and 1 fact table containing the count measure.
14. Degenerate dimension – mark correct answers:
a) Is used for attributes with low cardinality
b) Is directly stored in a fact table
c) Requires a new dimension table
d) Is used for attributes with high cardinality
✅ Best Answer: b) (and d) — A degenerate dimension is stored directly in the fact table without a separate dimension table (e.g., an order number, which has high cardinality).
21. In SCD Type 2:
a) Changes are tracked using separate columns in dimension table and allow preserving limited history
b) Surrogate keys are required to properly handle this SCD type
c) On change, overwrites old values with new values
d) Tracks historical data by creating multiple versions of a record in the dimension table
✅ Best Answer: d) (and b) — Type 2 preserves history by creating a new row for each change, which necessitates the use of surrogate keys.
31. Mark sentences which are true for Kimball's approach:
a) Focuses around the notion of conformed dimensions
b) Utilises normalized model for enterprise data warehouse
c) Focuses on multidimensional model for the data warehouse
d) Focuses on top-down approach – from data warehouse to data marts
✅ Best Answer: a) (and c) — Kimball uses a bottom-up approach (unlike Inmon's top-down) and heavily relies on conformed dimensions across multidimensional data marts.

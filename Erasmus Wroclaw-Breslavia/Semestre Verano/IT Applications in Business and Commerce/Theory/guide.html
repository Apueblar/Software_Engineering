Enterprise Applications, Distributed Programming & SOA

Lecture 1
Summary
Enterprise applications split logic into tiers (presentation, business, data) for reuse, faster time-to-market, and portability. Distributed objects evolved from RMI (Java-only) to CORBA (language-independent but firewall/security-unfriendly, binary), which motivated SOA — grouping functionality into autonomous, reusable services — and ultimately Web Services (SOAP/WSDL/UDDI), which ride on HTTP to avoid CORBA's firewall problems.
Concurrency Models
  • Sequential: efficient algorithms/data structures
  • Multithreading: solves I/O blocking; sync costs; Python historically one core
  • Processes: isolated, costly to create
  • Asynchronous: single-threaded event loop; avoid blocking calls
Distributed App Problems
  • Bottlenecks: databases, resource limits
  • Solutions: load balancing
  • Stateless applications
  • Sync primitives (semaphores, queues, TCP/IP)
  • Good pipeline design
Enterprise Goals
  • Reuse
  • Faster time-to-market
  • Lower cost, better quality
  • Portability — "write once, deploy anywhere"

Diagram — Distributed Programming Evolution
SOAP Message Structure

Envelope (required, wraps the message) → Header (optional, metadata) → Body (required, the actual call/data) → Fault (optional, error info)

✓ Web Services — Pros
  • Simple deployment
  • Firewall & security-friendly (rides HTTP/HTTPS)
  • Language-independent
✗ Web Services — Cons
  • Large XML messages
  • Historically "heavy" servers (less true with JAX-WS)
  • UDDI registries now rarely used — IBM/MS/SAP closed public nodes in 2006

REST, GraphQL & Microservices

Lecture 2
Summary
REST is an architectural style (not a standard) built on existing HTTP semantics: everything is a resource, addressed by a URI, manipulated with HTTP verbs (CRUD), and returned as a representation (JSON/XML/HTML). Classical REST has weaknesses — over/under-fetching, no built-in interface description — which GraphQL addresses by letting the client specify exactly what data it needs. Microservices extend SOA into fine-grained, independently deployable services, each with its own stack and data store.
1. Resource

Everything is a resource: customers, locations, items.

2. Name

Resources are addressed by a URI/URL.

3. Verb

CRUD via GET / POST / PUT / DELETE.

4. Representation

HTML, XML, JSON, or binary.

Diagram — CRUD ↔ HTTP ↔ SQL Mapping
SOAP vs. REST
SOAPREST
ProtocolHTTP / HTTPSHTTP / HTTPS
EndpointPath + SOAP envelopePath, HTTP methods, MIME type
ArgumentsXMLPath, query params, POST body
Data formatXML / XML SchemaJSON / anything
Interface descriptionWSDLNone standard — OpenAPI/Swagger by convention
XML vs JSON
  • JSON: shorter, JavaScript-native, has JSON Schema
  • XML: rich validator/tooling ecosystem, code generators, higher memory/CPU cost
Implementation Frameworks
  • Java: JAX-RS
  • Python: Flask, CherryPy, aiohttp, FastAPI
Problems with Classical REST
  • No built-in interface description (WSDL equivalent) — partially solved by Swagger/OpenAPI, but must be manually authored
  • Hard to handle nested/linked resources, includes/excludes
  • Over-fetching (generic endpoints) or under-fetching (specific endpoints → versioning problems)
  • Tight client-server coupling, outdated docs, response ambiguity
GraphQL
  • Originated at Facebook (2012/2015/2018 → GraphQL Foundation)
  • Client specifies exactly what data it needs
  • Reduces over/under-fetching
  • Supports multiple queries in one request
  • Not a database/storage/library — not tied to a transport (HTTP, WebSockets, etc.)
Microservices
  • Loosely coupled, fine-grained services, lightweight protocols
  • Independent stack & decentralized data (vs. monolith's shared stack/single DB)
  • Small, autonomous, cross-functional teams per service
  • Typically fronted by an API Gateway routing to Account/Inventory/Shipping etc.

Solutions range from polling and WebSockets to dedicated message-oriented middleware like AMQP/RabbitMQ (broker-based, producer→exchange→queue→consumer) and gRPC (Protocol-Buffers-based RPC over HTTP/2, supporting streaming).

Cloud Computing & Virtualization

Lecture 3, Part 2
Summary
Cloud computing (NIST: on-demand network access to a shared, rapidly provisioned pool of resources) rests on three pillars — virtualized, standardized, automated — enabled by data-center economies of scale. Virtualization (server hardware split into isolated VMs) is implemented via hypervisors using full virtualization, paravirtualization, or hardware-assisted techniques. Service models (IaaS / PaaS / SaaS) and deployment models (Public / Private / Hybrid / Community) describe how these resources are packaged and consumed.

Docker & Containers

Lecture 4
Summary
Containers solve "works on my machine" without the overhead of full VMs. Three Linux kernel features combine to make containers possible: namespaces (process isolation), cgroups (resource limiting), and copy-on-write filesystems (fast, shareable image layers). Docker commoditized LXC with a standard image format and reproducible Dockerfile builds; Docker Compose orchestrates multi-container apps on a single host.
Diagram — What Makes a Container
Unique Container Features
  • Run in user space; isolated but share the host kernel (no device emulation)
  • Own process space, network interface, /sbin/init
  • Near-native performance: CPU = native, memory = few % overhead
Docker on Different Platforms
  • Linux: native, uses host kernel cgroups/namespaces
  • Windows: Windows containers or Linux containers via WSL 2 (LinuxKit)
  • macOS: LinuxKit VM via HyperKit, own osxfs
  • Apple Silicon: ARM images by default; Rosetta 2 bridges to x86
Key Dockerfile Instructions
InstructionPurpose
FROMBase image to build on top of.
RUNExecute a command during image build.
COPYCopy files from host into the image.
WORKDIRSet the working directory for subsequent instructions.
EXPOSEDocument the port the container listens on.
CMDDefault command to run when the container starts.
ENVSet environment variables.
Multi-Stage Builds

Multiple FROM statements in one Dockerfile — one stage with full build tools (e.g. JDK), another slim runtime-only stage — keeps the final image small.

Security
  • Containers run as root by default — a risk
  • Mitigations: rootless mode, user namespace remapping, Enroot
GPU in Docker
  • NVIDIA drivers on host; libraries inside the image
  • docker run --gpus all
  • Compose: deploy.resources.reservations.devices
Alternatives
  • Podman: daemonless, rootless by design
  • Singularity: popular in HPC

TermDefinition
LXCLinux Container — lightweight OS-level virtualization that Docker commoditized.

cgroupControl group — kernel mechanism for limiting/accounting CPU, memory, I/O, network per process group.

A master/control plane manages worker nodes running Pods. GitLab CI automates build/test pipelines via .gitlab-ci.yml, triggered on push or schedule.

Cryptography & Security Fundamentals

Lecture 6
Summary
Symmetric ciphers (single shared key) are fast, used for bulk data. Public-key ciphers (key pair) are slow but solve key exchange and enable digital signatures. Hashes + MACs give integrity; signing a hash with a private key gives authentication, integrity, and non-repudiation — but never confidentiality.
Symmetric (Bulk) Ciphers
  • Single shared key — fast
  • Key size: 64–256 bits
  • Use: bulk data encryption
Public Key (Asymmetric)
  • Key pair; private not derivable from public — slow
  • Key size: 1024–2048 bits
  • Use: key exchange, digital signatures
Block Cipher Modes
ModeKey Point
ECBEach block independent — weak, identical plaintext → identical ciphertext.
CBCEach block XORed with previous ciphertext before encryption.
CFB / OFBTurns block cipher into a stream cipher.
CTREncrypts counter + nonce, XOR with plaintext — parallelizable.
OCBEncryption + integrity in a single pass.
Diagram — Digital Envelope (No Pre-Shared Secret)
Digital Signature — Signing
  • 1. Compute hash of the document
  • 2. Encrypt hash with author's private key
Digital Signature — Verifying
  • 1. Decrypt received hash with author's public key
  • 2. Recompute hash of the document
  • 3. Compare — equal ⇒ valid
What Digital Signatures Do / Don't Provide

✓ Provide: Authentication, Integrity, Non-repudiation.   ✗ Do NOT provide: Confidentiality (document stays plaintext).

Secure Network Protocols & Public Certificates

Lecture 7
Summary
A certificate lets a trusted third party (CA) vouch that a public key belongs to its claimed owner, solving the spoofing problem. Certificates follow the X.509 v3 standard (1996) and chain up to a self-signed Root CA. SSL/TLS uses this PKI to negotiate a cipher suite and session key over TCP — most visibly as HTTPS (port 443) — securing bank access and interbank transfers (SWIFT, ELIXIR).

📝Self-Check — Test Yourself
Why does a Root CA's self-signed certificate, by itself, not prevent spoofing?

Secure Electronic Payments

Lecture 8
Summary
Card payments split into POS (card present) and CNP/CNPT (card not present — phone/web) transactions; CNP carries the highest fraud risk because the issuer bank is liable for fraudulent charges. SET (MasterCard/VISA) was the first attempt at securing card payments online across four parties (cardholder, issuer, merchant, acquirer); it was superseded by 3D Secure (Verified by VISA / SecureCode), which routes authentication through the card issuer itself via SSL+XML. Mobile wallets like Google Pay go further, tokenizing the card so the real number never touches the phone.
CNP / Remote Transaction
  • Account name, card number, expiry + CVC2/CVV2/CID
  • Revocable — chargeback possible
  • High risk — issuer bank liable for fraud
POS Transaction
  • Offline credit (limited value), or
  • Online credit-limit validation, or
  • Charge card with online (delayed) charging
EMV
Europay/MasterCard/VISA chip standard
4
SET parties: cardholder, issuer, merchant, acquirer
3
3D Secure domains
NFC + SSL

  • Banks should not see what goods were purchased

Availability Calculations

Serial (all components must work): A = A_H × A_N × A_S × A_W. Example: 0.98×0.98×0.975×0.96 ≈ 89.89%.   Parallel/redundant (≥1 must work): A = 1 − (1−A_x)ⁿ. Doubling a 98% host → A_H = 0.9996, lifting the serial chain to 91.96%.

Lecture 15
Summary
Bitcoin's base layer throughput (~3.2 TPS) is dwarfed by VISA (tens of thousands of TPS), driving scaling proposals like SegWit and off-chain Lightning Network payment channels. Beyond Bitcoin's Proof of Work, alternative consensus mechanisms (PoS, LPoS, DPoS, dBFT) trade off security, speed, and decentralization. Smart contracts automate agreement enforcement and, when linked together, form DAOs — member-governed organizations with no central management. Real-world adoption now spans government, healthcare, finance, and logistics.

Proof of Work — Detail

Mining: collect → validate → bundle into blocks → compute SHA-256 hash → submit → earn reward.

sha256(sha256(data+nonce))=difficulty

Finding node broadcasts the block; others verify by reproducing the same hash; >50% acceptance = consensus.

Proof of Stake — Detail

All coins exist from genesis — no mining. A randomly picked node (lottery) adds the next block.

More staked coins → higher win chance. Winner collects transaction fees. Very energy efficient.

LPoS & DPoS — Detail

LPoS: small holders lease balance to a staking node (funds stay in their control); fees split proportionally.

DPoS: balance-weighted votes elect nodes; elected nodes then share equal lottery odds; holders can also vote on network parameters.

Smart Contracts — Complexity Spectrum

Digital value exchange → Smart right/obligation → Basic smart contract → Multiparty smart contract → Distributed autonomous business unit → Distributed autonomous organization (DAO) → Distributed autonomous government → Distributed autonomous society.

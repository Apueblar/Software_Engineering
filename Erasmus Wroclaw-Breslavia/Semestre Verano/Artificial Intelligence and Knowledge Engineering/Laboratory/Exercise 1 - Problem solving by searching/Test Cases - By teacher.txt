Test Cases — Assignment 1 (AI&KE)
The following test cases allow you to verify the correctness of your implementation. Each test targets a specific aspect of GTFS data processing and the algorithms. A solution that passes these tests should also handle harder edge cases.

Reference date: Unless stated otherwise, all tests assume the date 2026-03-04 (Wednesday) — a regular weekday within the timetable validity period.

A:         Wrocław Główny
B:         Jelenia Góra
Criterion: t
Start time: 06:00:00
Date:      2026-03-04

The earliest direct train is line D6 departing at 06:10 from platform V (stop_id: 1474651).

What it checks: If this test fails, verify: (1) whether the graph is correctly built from stop_times.txt, (2) whether the stop "Wrocław Główny" is properly mapped to its platforms (7 different stop_id values with parent_station = 1413380).

Test S1.2 — Multiple platforms at a single station
Aspect: Handling parent_station and transfers between platforms.

A:         Wrocław Główny
B:         Legnica
Criterion: t
Start time: 07:40:00
Date:      2026-03-04
Hints:

At 07:40, several trains depart from Wrocław Główny, including D20 (to Zielona Góra) and D40 (to Bielawa) — none of them go to Legnica.

Test S1.3 — Departure time ≠ arrival time at a stop (dwell time)
Aspect: Correct travel time calculation when a train stops for an extended period.

A:         Trutnov hl. n.
B:         Kamienna Góra
Criterion: t
Start time: 13:30:00
Date:      2026-03-04
Hints:

Trip D66 (37148513_397009): departs at 13:37 from Trutnov hl. n.
At station Kralovec, the train has an 11-minute stop (arrival 14:02, departure 14:13).
Arrival at Kamienna Góra: 14:31.
Total travel time from start: 61 minutes (13:30→14:31, including 7 min wait for the train).
On-train time: 54 minutes (13:37→14:31), not 43! — the dwell time at Kralovec is included.
What it checks: If the on-train time is 43 minutes, the algorithm ignores the difference between departure_time and arrival_time within a trip. The 11-min stop at Kralovec (14:02→14:13) is part of the journey. Edge cost (i, i+1) = arrival_time[i+1] - departure_time[i], but the total trip time must include dwell times (arrival_time[last] - departure_time[first] = 54 min, not sum(arr[i+1]-dep[i]) = 43 min).

Test S1.5 — Transfer minimization criterion (p)
Aspect: Switching the optimization criterion and the heuristic.

A:         Wrocław Główny
B:         Jelenia Góra
Criterion: p
Start time: 06:00:00
Date:      2026-03-04
Hints:

There are direct connections (0 transfers) — e.g., D6 at 06:10 or D60 at other times.
The algorithm with criterion p should return a route with 0 transfers.
If it returns a route with transfers (that happens to be faster), the criterion has not been switched correctly.
What it checks: Whether the A algorithm changes both the heuristic and the cost function g(n) when the criterion changes. For criterion p, g(n) = number of transfers (not time), and a distance-based heuristic *is not admissible. Expected heuristic: based on line structure (e.g., h=0 if n lies on a line reaching the goal, h=1 otherwise; or BFS on the line graph) — see heurystyki.md.

Test S2.3 — Cost asymmetry
Aspect: Time-dependent costs (time-dependent TSP).

A:         Wrocław Główny
L:         Legnica;Wałbrzych Główny
Criterion: t
Start time: 06:00:00
Date:      2026-03-04
Hints:

Compare two orderings:
Wrocław → Legnica → Wałbrzych Główny → Wrocław
Wrocław → Wałbrzych Główny → Legnica → Wrocław
The travel times will not be symmetric, because:
The waiting time for a train from Legnica to Wałbrzych depends on the arrival time at Legnica.
Legnica ↔ Wałbrzych have no direct connection (transfer required at Jaworzyna Śl. or Wrocław).
What it checks: If both orderings yield the same cost, the algorithm is probably using a static distance matrix instead of computing segment costs based on arrival time. In a correct implementation, the cost depends on the moment of arrival at each station.

Criterion: t
Start time: 06:00:00
Date:      2026-03-04

Run the algorithm with logging: at each iteration, print the current Tabu list state and the selected neighbour.

Does the Tabu list grow (task 2a) / get trimmed (task 2b)?
What it checks: Whether the Tabu list is properly updated and blocks revisits. If the algorithm cycles, |T| is too small or the Tabu list stores incorrect data.

Test S2.5 — Transfer criterion
Aspect: TSP with criterion p.

A:         Wrocław Główny
L:         Jelenia Góra;Legnica
Criterion: p
Start time: 08:00:00
Date:      2026-03-04
Hints:

Wrocław → Jelenia Góra: 0 transfers (D6 direct).
Wrocław → Legnica: 0 transfers (D1 direct).
Jelenia Góra → Legnica: ≥1 transfer (no direct connection).
Legnica → Jelenia Góra: ≥1 transfer.
Compare:
Wrocław → JG → Legnica → Wrocław: 0 + ≥1 + 0 = ≥1 transfer
Wrocław → Legnica → JG → Wrocław: 0 + ≥1 + 0 = ≥1 transfer
Both orderings have a similar transfer cost — but the waiting time for the transfer (and the possible 2-transfer variant) may differ.
What it checks: Whether the algorithm correctly counts transfers on each segment and sums them. Common mistake: counting transfers only on the segment with the highest number, instead of summing across the entire route.
